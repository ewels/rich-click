# A new website for rich-click

> The rich-click docs now run on Astro Starlight, with two new Starlight plugins and terminal output as text from rich-codex.

Today we launched a new website for `rich-click` 🎉 It is built with [Astro Starlight](https://starlight.astro.build/) instead of MkDocs. It’s beautiful, fast and modern. The site took a little time due to several detours, notably updates to [rich-codex](https://github.com/ewels/rich-codex) and the creation of two new Starlight plugins: [Starlight Pydocs](https://ewels.github.io/starlight-pydocs/) and [Starlight Codeblocks](https://ewels.github.io/starlight-codeblocks/). In this blog post I dive into what changed, and why. The main changes that you’ll be able to see in the new site are: * A redesigned homepage which is hopefully more interesting to look at and that does a better job at conveying what `rich-click` does. * A new [Quickstart](../../documentation/quickstart/) page. * Terminal output is now text, not screenshots. You can select it, search it and copy it, and it follows the light or dark theme. * An auto-generated [API reference](../../api/rich_click/), generated from the `rich_click` source. A badge on each object tells you which release added it. * Names in code examples link to the Click, Rich and Typer docs, with a card that opens when you hover. * Every page is also served as Markdown, and the site publishes `llms.txt`. You can give the docs to an AI assistant with one click. ![The new rich-click homepage: the logo and tagline on the left, and a terminal on the right showing rich-click help text, with buttons to switch colour scheme and format.](/rich-click/latest/_astro/homepage.CpxqgE-g_ZboegI.webp) The new homepage. Pick a colour scheme and a format, and the terminal on the right updates. Psst: try clicking the logo. ## Why move off MkDocs [MkDocs](https://www.mkdocs.org/) has had no maintainer since August 2024. Its planned v2 drops support for existing themes, plugins and config files. [Material for MkDocs](https://squidfunk.github.io/mkdocs-material/), the theme we used, reaches [end of life](https://squidfunk.github.io/mkdocs-material/blog/2026/02/18/mkdocs-2.0/) on 5 November 2026. In August I moved the rich-click website to build using [ProperDocs](https://properdocs.org/), a fork of MkDocs 1.x, in PR [`#341`](https://github.com/ewels/rich-click/pull/341). That kept the site building, but only really as a stopgap. [Zensical](https://zensical.org/) is the official successor to Material for MkDocs, but it’s still at a fairly early stage of development and is missing functionality such as supporting blogs, our RSS feeds or custom plugins. I have been a big fan of [Astro](https://astro.build/) for a while now, including its official documentation theme, [Starlight](https://starlight.astro.build/). It’s fast and modern, with good developer tooling. It looks good out of the box and has a lot of clever tricks with how it bundles outputs, resulting in exceptionally [eco-friendly](https://starlight.astro.build/environmental-impact/) websites: a first visit to a Starlight page typically downloads less than 50 KB of compressed data, about 2.5% of the median web page. On the same day as PR `#341`, I asked Claude to rebuild the whole site using Astro Starlight, with the same URLs, styles and features. The first build was pretty decent: * Every page, blog post, redirect and old feed URL still resolved. * Versioned deploys kept the `gh-pages` methodology that [`mike`](https://github.com/jimporter/mike) used. The 1.8 docs, built with MkDocs, stay as they are and stay in the version picker. * A full build only takes about 15 seconds. I opened the result as a proof of concept in [#342](https://github.com/ewels/rich-click/pull/342) and asked my `rich-click` co-maintainer [Daniel Reeves](https://github.com/dwreeves) for his thoughts, with no plan to merge it soon. He liked it, but had a few suggestions.. ## starlight-pydocs: API docs from docstrings Daniel had wanted API docs for a long time - we’d discussed it previously but never got around to putting the time in to figure them out. On MkDocs the obvious tool is [mkdocstrings](https://mkdocstrings.github.io/), but there was no Astro / Starlight equivalent. To make matters worse, whilst MkDocs is built in Python, Astro / Starlight are NodeJS projects, requiring a totally different tool chain. However, there was a glimpse of hope: in [his review](https://github.com/ewels/rich-click/pull/342#issuecomment-5247648331) he pointed out that mkdocstrings keeps its Python parsing in a separate library, [Griffe](https://mkdocstrings.github.io/griffe/). He suggested that a general Starlight plugin on top of Griffe could be a good open source project. I was well and truly nerd-sniped 🎯 Four days later I published [starlight-pydocs](https://ewels.github.io/starlight-pydocs/) 0.1.0, and the `rich-click` branch had an API reference. Like the site itself, I built it with Claude Code. Claude first read how other Starlight plugins work, such as [starlight-openapi](https://starlight-openapi.vercel.app/) and [starlight-typedoc](https://starlight-typedoc.vercel.app/). It wrote a plan from that, and then built the plugin step by step. The plugin runs Griffe either as a prerequisite step, or as a subprocess during the website build. Griffe reads the source by static analysis, so nothing is imported and your package does not need to be installed. You only need `uv` on your path. The plugin takes the Griffe output JSON and uses it to render one page per module, with a sidebar tree that follows the package layout. It reads Google, NumPy and Sphinx docstrings, and it renders their prose with your site’s own Markdown pipeline. Two pretty neat features are *type links* and *version badges*. For type links, the plugin reads Sphinx inventories, so `click.Command` in a rich-click signature links to the Click docs. For version badges you give the plugin a list of git refs, and it extracts the API at each ref and badges every object with the release that added it. The plugin also publishes an `objects.inv` and an `llms.txt` for each package, so other sites and AI tools can link to your API. It is on the [Starlight plugins list](https://starlight.astro.build/resources/plugins/), and it also works on Astro sites that do not use Starlight. ## starlight-codeblocks: code blocks that do more Starlight renders code blocks with [Expressive Code](https://expressive-code.com/). It gives you titles, line highlights and diff markers. But now that I’d written one Starlight plugin, I started to dream about what else I could build. Code examples are the heart of any documentation site, and I started thinking about all the cool things I’ve seen across my favourite websites over the years: notes on lines, links from code to API docs, and output under a command. And so, [starlight-codeblocks](https://ewels.github.io/starlight-codeblocks/) started as a separate project in late September. This time I wrote a design pack before any code: a spec for 24 features, with HTML mockups that showed how each one should look and behave. I gave the pack to Claude with a kick-off prompt that said to work through the plan without stopping to ask questions. Version 1.0.0 came out on 5 October, and the plugin now has 27 distinct features. It builds on Expressive Code, so the code blocks you already have keep working. This plugin also handles API auto-linking. Names in any Python code blocks link to their docs, with a hover card. The plugin uses the same Sphinx inventories as Starlight Pydocs, so now all free-form code blocks in the docs also link to their API docs. It also has features for annotations (see the new [Quickstart](../../documentation/quickstart/) page) and some cool tricks up its sleeve such as being able to use WebAssembly to run Python code in the browser for examples. When both plugins are installed, they find each other with no configuration. The generated API pages get the hover cards, and long docstring examples collapse. ## rich-codex: terminal output as text The final piece in the puzzle was [rich-codex](https://github.com/ewels/rich-codex). It’s a project I wrote a while back which finds commands in your Markdown, runs them, and saves the terminal output as an image. It has made the terminal screenshots for rich-click since 2022. A GitHub Action runs it on every push, so the screenshots stay in step with the code. It had three releases to support the new rich-click website build as I went along: 1. MDX support. Starlight pages that use tabs or other components are MDX, and MDX does not allow HTML comments. Since August, rich-codex also reads its config from JSX comments: `{/* RICH-CODEX ... */}`. 2. Embedded fonts. An SVG inside an `<img>` tag cannot load a web font. If you did not have Fira Code installed, the box lines of a rich-click panel came apart. A user had actually reported this in [rich-codex #65](https://github.com/ewels/rich-codex/issues/65), and this was the nudge I needed to solve it. Since rich-codex version 1.4.0 in September each SVG carries a subset of Fira Code. 3. Output as text. Now that I had Starlight Codeblocks working so well with WebAssembly output, it seemed strange to be embedding SVGs everywhere. I didn’t want to run hundreds of examples in the browser, so instead as of version 1.5.0 (released today), rich-codex can save output as an `.ansi` file instead of an image: plain text with the ANSI colour codes kept. The third change was a fun one. It required changes across rich-codex, Starlight Codeblocks and the rich-click docs, all in unison. The rich-click docs now have examples in their markdown files that look like this: 
````mdx
{/* RICH-CODEX working_dir: docs/code_snippets/introduction_to_click */}
```sh runnable.outputFile="../images/code_snippets/introduction_to_click/hello_help.ansi"
$ python hello.py --help
```
````
 rich-codex reads the comment, runs `python hello.py --help`, and writes the coloured output to the `.ansi` file. Starlight Codeblocks then reads that file at build time and shows the output under the command. It converts the ANSI codes to colours based on the site theme, and adjusts any colour that has less than `4.5:1` contrast against the output background. Here is the example from our README, as the new text output and as the old SVG screenshot: * New: text output

 

 * Old: SVG screenshot ![SVG screenshot of the help text from python examples/11\_hello.py –help](/rich-click/latest/_astro/hello.DIVhSJ2q_ZnIMtk.svg) The rich-click site now has 96 of these `.ansi` files in place of SVG screenshots - hopefully you’ll agree they look great, and should be quite a bit easier to maintain. ## Use them on your own site I finally merged the site rewrite PR today, three months after I opened it as an experiment. Thanks to Daniel for the review, and for the idea that became Starlight Pydocs. None of the three tools mentioned is specific to rich-click: * [starlight-pydocs](https://ewels.github.io/starlight-pydocs/) works for any Python package. Install it with `npm install starlight-pydocs`. * [starlight-codeblocks](https://ewels.github.io/starlight-codeblocks/) works on any Starlight or Astro site. Install it with `npm install starlight-codeblocks`. * [rich-codex](https://github.com/ewels/rich-codex) runs as a GitHub Action or from the command line, and its `.ansi` output works with any tool that reads ANSI colour codes. Both the Starlight plugins ship an agent skill, so you can ask your coding agent to set them up. I hope you like how the new site looks, and perhaps find the tools that spun off to be useful. If something breaks, or if you want a feature, please open an issue on GitHub.

We’ve fleshed out the documentation from the README, and we’ll continue to add to it over time. ### Live Style Editor The coolest addition allowed by this change to full documentation is the [Live Style Editor](https://ewels.github.io/rich-click/latest/editor). We built this to address a problem we noticed, which is that the vast majority of users rely on the default **rich-click** styles. Although we do think **rich-click**’s defaults are pretty good, it pointed to a potential developer experience issue that so many CLIs relied on the defaults. We hope that the live style editor makes it easier for users to make style changes and to personalize their CLIs. 😁 Here is an example of a style that Phil made with the style editor: ![](/rich-click/latest/_astro/phils_example.ClP8a0Nl_Z7P3B.svg) And here’s one that Daniel made: ![](/rich-click/latest/_astro/daniels_example.BTRRF9wm_Z7P3B.svg) ## **rich-click** version 1.8 ### Generate HTML and SVG with the `rich-click` CLI The `rich-click` CLI now allows for `--output svg` and `--output html` to help easily generate outputs for READMEs and docs: 
```shell
rich-click --output svg path.to.my.cli:main --help
```
 ![](/rich-click/latest/_astro/output_to_svg.d1cf5lQS_Z1kMKXF.svg) ### Easier decorator API The `rich_config()` decorator API is now easier to use: You can pass a `dict` into the `@click.rich_config()` decorator. E.g.: 
```python
@click.command
@click.rich_config(help_config={"max_width": 100})
def my_command():
    ...
```
 Additionally, `dict`s behave a little differently than `RichHelpConfiguration` when dealing with parents, and this behavior can be useful in some contexts. Basically, the child command uses the parent’s help config as a baseline, and only updates the fields specified in the dict. So in the following example, `my_group` will have `style_option="red"`, and `my_subcommand` will have *both* `style_option="red"` and `style_argument="green"`. 
```python
@click.group
@click.rich_config(help_config={"style_option": "red"})
def my_group():
    ...


@my_group.command
@click.rich_config(help_config={"style_argument": "green"})
def my_subcommand():
    ...
```
 This can be a little confusing, so we’ve defined explicit rules (and enforced them in unit tests) for how the config is resolved (these are also in our docs): 

 ### More style options The biggest addition to **rich-click**’s styling options was control over panel styles: * `STYLE_OPTIONS_PANEL_BOX` * `STYLE_COMMANDS_PANEL_BOX` * `STYLE_ERRORS_PANEL_BOX` Here’s a silly example of what this can do: ![](/rich-click/latest/_astro/boxes_silly.D6neGPuC_12rlaQ.svg) Here’s a simple, stylish, and sleek example that would look great in your app: ![](/rich-click/latest/_astro/boxes_sleek.my2Qxpzx_ZVrudv.svg) ### Improvements to option and command group API The option groups and command groups are a very powerful and useful feature, but historically they’ve been tricky to work with. The changes we’ve made in 1.8 improve on the API in a few substantial ways. #### Better command path resolution First, group keys used to only read from the `ctx.command_path`. Now they read from the `ctx.command_path` and the `ctx.command.name` (or the `f"{ctx.parent.command.name} {ctx.command.name}"` for subcommands). This should cause fewer headaches for users! cli.py 
```python
import rich_click as click


# Pick your poison 🧪 Both approaches now work!
click.rich_click.COMMAND_GROUPS = {
    "super-cool-tool": [...],  # `ctx.command.name`
    "cli.py": [...]  # `ctx.command_path` when running "python cli.py".
}


@click.command("super-cool-tool")
def main():
    ...
```
 #### Wildcards Wildcards now also work, in case you want to globally define options or simply don’t want to bother spelling out the whole command path. 
```python
import rich_click as click


click.rich_click.COMMAND_GROUPS = {
    "*": [...],
}


@click.command("super-cool-tool")
def main():
    ...
```
 You can also stick wildcards in the front, middle, or end of a key, e.g.: * `cli sub-command *` * `cli * sub-sub-command` * `* sub-command *` #### `panel_styles` + Arguments panel styling The dicts for command+option groups now accept an optional `panel_styles` key, which passes kwargs to the `Panel()`. Another handy feature is that the “Arguments” panel (which is created when the config option `show_arguments` is `True`) can now be stylized through the API so long as the following is true: 1. `config.show_arguments` is `True`. 2. There is an option group with a `name` equal to the `config.arguments_panel_title` (default: `'Arguments'`) 3. The option group does not have any `options` (The list is empty, undefined, or `None`). Example: 
```python
import rich_click as click
from rich import box


help_config = click.RichHelpConfiguration(
    show_arguments=True,
    option_groups={
        "my-command": [
            {
                "name": "Arguments",
                "panel_styles": {"box": box.DOUBLE_EDGE, "border_style": "dim red"}
            }
        ]
    }
)


@click.command("my-command")
@click.argument("foo")
@click.argument("bar")
@click.option("--baz")
@click.rich_config(help_config=help_config)
def cli(foo, bar, baz):
    ...


if __name__ == "__main__":
    cli()
```
 ![](/rich-click/latest/_astro/arguments_box_and_panel_styles.BvnVrfSD_Z23PWeI.svg) ### Improved performance During command execution, **rich-click** now loads faster and takes up less memory than before: ![](/rich-click/latest/_astro/execution_times.CMMRdAuz_Li4QK.webp "Execution times of different CLI frameworks") ![](/rich-click/latest/_astro/memory_profiles.ChTE-U5O_Z2reBlm.webp "Memory consumption of different CLI frameworks") We include the code we ran below. The metrics you see above were gathered by running the below script on an old Macbook. We include Typer in our profiling to show a reasonable baseline for a Click wrapper’s overhead. Typer is an ambitious and great project that’s doing quite a bit under the hood, and it’s reasonable to expect it to take a little more time and memory. Why is **rich-click** 1.8 more performant? 1.7 left a few free optimizations on the table: 1. Only import `rich` when rendering help text. 2. Use `click.__version__` instead of `importlib.metadata.version("click")` for Click 7 compat. For the first change, this meant replacing code like this…: 
```python
from typing import IO, Optional


from rich.console import Console


from rich_click.rich_help_configuration import RichHelpConfiguration


def create_console(config: RichHelpConfiguration, file: Optional[IO[str]] = None) -> Console:
    console = Console(
        # ...
    )
    return console
```
 …with code like this…: 
```python
from typing import TYPE_CHECKING, IO, Optional


from rich_click.rich_help_configuration import RichHelpConfiguration


if TYPE_CHECKING:
    from rich.console import Console


def create_console(config: RichHelpConfiguration, file: Optional[IO[str]] = None) -> "Console":
    from rich.console import Console
    console = Console(
        # ...
    )
    return console
```
 …so that Rich is only loaded when it is needed! Combined, these two changes account for the performance improvements you see. Performance isn’t everything; if it was, we’d all be using `argparse`, or we’d abandon Python altogether for Rust. This is also peanuts in the grand scheme of things. In all likelihood, you’ve spent more time reading this blog post than the cumulative amount of time you’ll save by `pip install --upgrade`-ing your **rich-click** 1.7 project. (There are other reasons to upgrade to 1.8 than performance, of course!) So why bother improving **rich-click**’s performance if it’s not a big deal? Because we’re honored every time someone chooses **rich-click** for their applications, and we want to pay it back by keeping things as efficient as we reasonably can. Your application is complex and special and all yours. We’re excited we get to be a very small part of what you’re doing, 🫶 and we’ll do our best to keep our end of things neat and tidy. ### And more… Under the hood, we’ve done misc. bugfixes and other small internal improvements+refactors, mostly aimed at composability and customizability for advanced use cases. (This does not impact 99% of users.) ## Plans for the future **rich-click** is not done evolving; 1.8 is just another step on the journey. We already have tons of things planned out for 1.9, which we want to release by the end of 2024. Before we get there, we are going to spend a little bit of time rewriting and reorganizing our unit tests and adding coverage requirements. Thank you once again for using **rich-click**! ❤️❤️❤️❤️❤️

In the below example, we patch typer to use the `star-slim` theme directly in the CLI code: Under the hood, we are doing metaclass [dark magic](https://github.com/ewels/rich-click/blob/e57aa800555bb8f3e3c46582f61fb22080802f4b/src/rich_click/patch.py) to prevent needing to preemptively import Typer, and to prevent requiring users to specify that a CLI is a Typer CLI. This feature is still experimental, so please let us know if you encounter any bugs. ## Panels Panels are a big new feature of **rich-click**, and bring along with it an intuitive and powerful API for customization. Panels replace the old “groups” feature of previous **rich-click** versions. (Don’t worry, your old code will still work just fine.) This is something I’ve wanted in **rich-click** for a long time, as I’ve always found the old groups API powerful but a little hard to use. With the new API, defining a panel is as simple as adding a decorator. 
```python
import rich_click as click


@click.command()
@click.argument("src", help="Source", panel="Main")
@click.argument("dest", help="Destination", panel="Main")
@click.option("--env", "-e", help="Environment", panel="Extra")
@click.option("--log-level", "-l", help="Log level", panel="Extra")
@click.version_option("1.2.3", "--version", "-V", panel="Extra")
@click.help_option("--help", "-h", panel="Extra")
@click.option_panel("Main")
@click.option_panel("Extra")
@click.rich_config({"theme": "star-nu", "max_width": 80})
def move_item(src, dest, env, log_level):
    """Move an item from a src location to a dest location"""
    pass


if __name__ == "__main__":
    move_item()
```

We now support a `help` kwarg for arguments. ### Aliases: `@Group().command(..., aliases=[...])` **rich-click** commands can now be given **aliases**, similar to other Click extensions ([click-aliases](https://github.com/click-contrib/click-aliases/tree/master), [click-extra](https://kdeldycke.github.io/click-extra/), [cloup](https://cloup.readthedocs.io/en/stable/)). ### `rich-click` CLI supports `path/to/file.py` Now, all the following ways of invoking the `rich-click` CLI are supported: * `rich-click hello:cli --help` * `rich-click hello.py --help` * `rich-click hello --help` In prior versions, only the first way worked. ### Smarter newline handling in command help text We are now a little more careful and practical with how we handle newlines in help text. You can see a demo of rich-click 1.9’s newline handling below: ### Stderr help: `context_settings={"help_to_stderr": True}` Print help text to stderr with a context setting! ### Deferred help text rendering Like normal Click, now help text is pushed to a buffer and rendered at the very end of the help text generation context. Most users won’t notice a difference, but it makes help text rendering atomic (e.g. in the event of an error), and also assists with integrating into tools such as [mkdocs-click](https://github.com/mkdocs/mkdocs-click). ### Many other minor improvements There have been so many tiny changes to **rich-click** over the past few months that I’ve lost count. We are being a little more conservative than we perhaps need to: Click 8 came out in 2021, Rich 12 came out in 2022, and Python 3.8 came out in 2019 and hit end-of-life in 2024. That said, we don’t believe there is a major cost to supporting these other than some slightly ugly backend code here and there, so we’ll continue to be conservative with dropping support. Additionally, there are a handful of additional pending deprecations introduced to config options: * `show_metavars_column` * `append_metavars_help` * `option_envvar_first` * `use_markdown_emoji` Of these config options being deprecated, the most popular is the combination of `append_metavars_help=True` and `show_metavars_column=False`. We deprecated support for these because in 1.9, this is handled via declaring order of elements explicitly with the config options `options_table_column_types` and `options_table_help_sections`.
